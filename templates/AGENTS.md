- 建议要诚实：方案或用户的提议有问题就直说。

## 2. 角色

- 主协调器是用户当前会话：裁决、计划、Git、收货。
- 子代理（`.claude/agents/`）：侦察 `bs-scout`、执行 `bs-exec`、核心执行 `bs-core`（前端、复杂与关键实现）、设计 `bs-design`、复核与顾问 `bs-review`、验证 `bs-verify`（不能由本轮实现者兼任）。
- 子代理不做 Git 操作，不删除用户持久数据。任务书开头用 `beanstack` 的 `references/prompt-preamble.md`。

## 3. 工作流程

1. 非简单任务的第一条回复先对齐：复述目标和最小改动，写出外部检验点；只在第 4 节停止条件处停下问。
2. 探索 → 提案 → 行为改动先写会红的测试 → 派子代理实现，只跑受影响验证 → 用户体验验收 → 收尾：合入最新主干、按风险复核、开 PR。一句话改动直接改、验证、提交。
3. 有推荐方案就按推荐做，取舍写进交付。用户本轮提的事和开发中发现的缺陷本轮修完。
4. 用户每轮提的事逐条写成需求条目（要变什么、保持什么、验收画面）并落盘，上下文压缩后以落盘的为准。<!-- TODO: 需求条目存放位置或工具 -->
5. 做不到用户原话时，不用兜底档、降级显示或「结果打了折扣」的提示包起来：这一条记不通过，只开 PR，由用户看了再定。
6. 条件授权（如「绿了就合并」）只在需求条目全部关闭时成立（有当前代码上的证据，或用户针对条目的放行原话），否则只开 PR 并列出未关闭条目。
7. 真机、真支付、真麦克风、真外链这类本机测不了的条目，立表时标「本机测不了」，交付里单列，事后不改标成别的。
- **分支与 PR**：一个 worktree 一个分支一个 PR；<!-- TODO: 分支命名与 PR 模板 -->。
- **独立复核**：改到部署链、CI、迁移、money、auth、权限、对外契约、依赖清单时必须复核，复核者不能是作者；其余在交付注明「未做独立复核」。

**交付总结**：开头一句说什么在等用户拍板（没有就说没有），结论标实测、推断或未验证。① 这一轮做了什么；② 修改前后对照（改动项｜修改前｜修改后｜验证），分「你提的问题」和「自己发现并修好的问题」；③ 过程中的决定（问题 → 怎么定的 → 理由）；④ 需要用户决定或授权的事。小改动写一两行。

## 4. 停止条件

只在这些情况停下问：产品或用户可见行为的取舍没有定论；不可逆或对外的操作（合并、发版、部署、删数据、对外发布）；money、auth、权限、安全边界的语义变化或破坏对外契约；缺只有用户能给的信息或凭据。确认收尾不等于授权合并。

## 7. Git、合并、发版、部署

- Git 只由协调器操作；例外是隔离 worktree 里的子代理在自己的临时分支上 commit，由协调器 merge。
- hooks 报错修根因，不绕过。提交用 Conventional Commits。
- 合并、发版、部署分别授权，授权只认用户针对该操作的原话；原话含否定说法时整条拒绝。<!-- TODO: 合并、发版、部署的具体命令 -->
- 线上出问题先回滚到上一个已发布版本，再查根因。

## 8. 安全底线

- 不删除或清空用户持久数据，只清理自己创建的临时资源。
- 已发布迁移不可修改；破坏性 DDL 走 expand/contract。
- 口令、密钥、cookie 不进仓库、不进日志。
- 生产环境的写操作、数据修复、配置变更都属于停止条件。

## 10. 维护本规范

- 改本文件需要用户同意。每一行都要回答「删掉它，智能体会不会犯错」；平实语气，不堆强调词。
- 被纠正时先修错；规则已在却没有强制它的机制导致重犯的，同一改动里按 架构 > 类型 > 断言 > 测试 > lint > 文档 升级，新检查要在一次真实旧错误上变红；错误已不可能再犯就删规则。
- 每次都要知道的放这里；某目录才用的放目录 `AGENTS.md`；通用流程放 `beanstack`；必须每次发生的检查做成钩子或守卫。
- 新增门禁、守卫、钩子前，写清它防的真实事故，并说明能删掉哪个旧机制。
