# BeanStack

项目 `AGENTS.md` 定义底线、停止条件和命令，本技能讲通用做法，不一致时以项目为准。reference 按需读：

| 需要什么 | 读哪个 |
|---|---|
| 开工对齐：复述、行话、改深 | `references/align.md` |
| 根因与架构裁决、唯一安全事实 | `references/architecture.md` |
| 工程原则索引 | `references/principles.md` |
| 选验证方式、TDD、性能数字、持续优化一个指标、运行时取证、同类排查清单 | `references/verification.md` |
| 并发、重试、状态机的形式化验证与状态图 | `references/formal-verification.md` |
| 派不派、怎么派、调度模式、换通道 | `references/dispatch.md` |
| 子代理任务书开头 | `references/prompt-preamble.md` |
| 角色 → 模型、档位、路由表 | `references/model-roster.md` |
| 外部 CLI 启动器 | `references/external-cli.md` |
| 用户问进度、长任务后汇报 | `references/progress.md` |
| 讲解怎么工作、为什么、字幕幻灯片视频 | `references/explain.md` |

## 分流

| 任务 | 步骤 |
|---|---|
| 一句话改动 | 直接改 → 受影响验证 → 提交 |
| bug | 先在当前基准上复现（可能已修好）→ 失败测试 → 修复 → 同一表面转绿 |
| 功能 | 探索 → 提案 → 验收测试 → 分单元派执行 |
| 重构 | 画系统模型 → 裁决 → 补测试锁住现有行为 → 迁移全部调用点 → 删旧路径 |
| 性能 | 固定负载和设备测基准 → 定位（卡顿、泄漏先做运行时取证）→ 按「不做 → 不重复 → 少做 → 晚做 → 并发 → 更便宜」找修法 → 同条件复测，报前后数字 |
| CI、部署、迁移 | 读项目领域规则 → 提案 → 实现 → 异系复核 |
| 规则、技能、文档 | 改 → 链接与结构自查 |

除一句话改动外，第一条回复先按 `references/align.md` 对齐，最后都走 体验验收 → 冻结 → PR，合并、发版、部署各等用户授权；发现更重时升级流程并告诉用户。步骤写进 todo，不做的写 `skip: <原因>`。

## 技能触发（装了才用）

| 场景 | 技能 |
|---|---|
| 各阶段 | 探索 `openspec-explore`；提案 `openspec-propose`；改已有变更 `openspec-update-change`；实现 `openspec-apply-change`；冻结 `openspec-verify-change` → `openspec-archive-change` |
| 任何视觉产出 | 动手前读项目设计规范相关条款，加载 `frontend-design` + `impeccable` |
| 新页面、整页改版、重新设计 | 使用 Claude 宿主时优先用 **Claude Design** 出原型与视觉定稿，再按项目设计规范 token 1:1 还原（其余宿主走 `references/dispatch.md`「设计稿先行」） |
| 动效 | 新建 `animate`（按需 GSAP、`threejs-*`）；评审 `review-animations` / `improve-animations` |
| 用户可见中文文案 | `humanizer-zh` |
| 用户问进度、隔很久回来；并行任务收货后汇报 | `references/progress.md` |
| 「怎么工作」「为什么这样」「讲给我听」、要视频 | `references/explain.md` |
| 竞态、锁、重试、状态机、同步协议，或同类 bug 修过两次 | `references/formal-verification.md` |
| 测出或要报告一个性能数字 | `references/verification.md`「性能与数字」 |
| 要把一个指标反复推到目标（准确率、速度、包体） | `references/verification.md`「持续优化一个指标」 |
| 卡死、泄漏、抖动、CPU 飙高，或拿到了性能录制、日志 | `references/verification.md`「运行时取证」 |
| 接手上一个会话、压缩后续做 | 以已有记录为准（需求核对表、任务笔记、提交）：先列已完成和待做，不重做已完成的；继承来的「已通过」对照原始目标在真实产物上核一遍 |
| 小 diff 但不放心、改动牵连远 | `references/architecture.md`「唯一安全事实」 |
| 没有先例的设计或交互分叉 | 一次性原型（`references/architecture.md`）或多候选（`references/dispatch.md`） |

UI 派工：技能不会被子代理继承，任务书写明要读的规范章节和要加载的技能，值只引用规范原文或 token 名；外部 CLI 把条款和 token 值摘进任务书。基线是主干实现，没点名的不改；需求和规范冲突时停下裁决。

## 各阶段

**对齐**：按 `references/align.md` 复述目标、补行话、改深，外部检验点写进验收判据；术语与现成方案的检索和代码侦察并行。

**探索**：从真实入口追到状态所有者、持久化、边界和副作用；代码侦察与外部检索并行，检索结论核实后才写进根因。产出根因机制、关联问题、推荐方向。要问用户时先查清事实，把前置已定的决定一次问完，每题给推荐答案。

**提案**：proposal 写架构裁决（`references/architecture.md`）。tasks 按可独立验收的单元写，每项有判据、验证、写入范围。

**先写测试**：行为改动先红、单独提交，再实现（`references/verification.md`）。

**实现**
- 修完整：根因、所有受影响调用点和同类缺陷一起修，被替代的旧路径删掉。发现一个问题先排查同类，列清单一次修完再验证。
- 独立单元并行派出；每完成一个可验证阶段就提交推送。两次修复没过同一关，先写下并验证它们共同的前提（攻击前提），再写下一个修复。
- bug 的任务书列出共享同一机制的其它入口，每个一条测试或排除理由。

**体验验收**
- 核对表落在项目 `AGENTS.md` 指定的位置（项目有落盘工具就用工具，没有就写进 OpenSpec tasks 或任务笔记文件，不只留在对话里）。每条写入口、要变什么、保持什么、验收画面；用户附图是第一份验收输入；保持项用改动前后同路径截图对照。
- 交出去前按用户路径逐条走（开关打开、有数据的登录账号、共享机制的每个入口）；设计稿逐属性对照，测试里的视觉值取自设计稿。
- 做不到原话记不通过，不包装成降级；本机测不了的立表时标出，只用替身验证的写「未实测」。用户第二次报同一问题先用真实输入复现。
- 交用户时说明分支、启动方式、看哪里；反馈修复只复验受影响的。

**冻结**（用户确认收尾后）
1. 合入主干最新代码。
2. 按项目风险分级复核：复核者只拿需求、判据和 diff；finding 要能复现，同类报成一条；确认的先写成会红的测试再修，修复 diff 交原复核者确认一次。
3. OpenSpec verify → archive，提交变更片段。
4. 开 PR 前只跑推送前检查；改到路由、懒加载或依赖时跑构建与包体预算。
5. 复盘：从本轮对话里挖持久的教训（用户的纠正、自己摸索出的命令和坑、本可自己查到却让用户提供的信息、没在真实产物上跑的检查、该用没用的技能），每条落到某个技能或规则的具体修改；能由守卫、lint、脚本强制的按项目规则升级成结构，不加文字。只保留半年后仍成立、会改变下一个代理做法的；改规则文件先给用户看。

**PR**：仓库有 PR 模板就用模板；没有就用这几个二级标题，空的省略：Why、What changed、Scope、Tradeoffs、Blast Radius（写唯一安全事实）、Verification，正文 40 行以内，长证据放评论或文件。门禁红先分清代码还是基础设施问题；代码问题修完想清楚推送前检查为何没拦住。

**合并、发版、部署**（三件事各要用户明确授权；用户确认收尾不等于授权合并）
- 只走项目规定的合并入口（合并队列、门禁脚本），记下授权原话；门禁全绿才合，红了等失败出齐一次修完再推。
- 条件授权（「门禁绿了就合并」「做完直接发版」）只在需求条目全部关闭时成立：每条有当前代码上的证据，或用户针对该条的放行原话；否则只开 PR，停下列出未关闭的条目。
- 授权原话带限定或否定（「先别部署」「只发内测」）时按最窄的范围执行，拿不准就整条不执行并问。
- 部署后跑冒烟、看错误率；线上出问题先回滚到上一个已发布版本，再查根因。
- 合并后清理本轮的分支、worktree 和临时资源，把授权与门禁结论记进任务笔记。

## 收货

- 亲自读驱动裁决的关键源码和 findings，其余核对真实输出与退出码。后台任务一结束就收货。
- 不达标默认新派子代理，带原任务书、之后的全部指示、上一轮报告和分支；只有返工要用原子代理的未提交改动、正在跑的进程，或缓存未过期且返工很小时才续它。报「不可行」要它给卡住的证据。两轮不过就诊断派工本身（缺信息、假设错、能力不足、环境），按 `references/model-roster.md` 的阶梯升级。
- 其他问题默认本轮修；命中停止条件的交用户；大到无法和本轮一起验收或回退的，留证据按项目规则提 issue。用户本轮提的事不转 issue。

## 交付

按项目 `AGENTS.md` 的交付格式，逐条对用户本轮的问题。开头一句说什么在等用户；每个结论标实测、推断或未验证；待决事项按 `references/progress.md` 写到只看回复就能拍板。另补：

- **模型使用**：按 `scripts/channels.sh --ledger` 汇总，含失败与额度耗尽的通道。
- **检索是否起作用**：命中、给了方向或没用上。
