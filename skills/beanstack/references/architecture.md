# 架构先行

先看顶层逻辑是否合理，再决定修、局部重构还是重设计。不改数据流、不改边界、不新增路径的小修可以直接修。

- **系统模型**：从真实入口追调用链 → 状态所有者 → 持久化 → 边界 → 副作用，每步有文件证据；答清唯一写者、全部读写路径、现在的形态是设计的还是补出来的（`git log -S`）。分清事实、推断、未知。
- **关联扫描**：同机制、同数据路径、同调用模式、历史修过几次；同根因的本轮一起修，扫描为空也写明查过哪些方向。
- **补丁气味**：新开关绕过既有路径、调用点特判、复制相似逻辑、下游补上游、吞异常或用 retry/延时掩盖竞态、为变绿改测试、修复面积与机制不匹配。命中就在裁决里解释或换方案。
- **唯一安全事实**：看着有风险的改动，大多因为某一个事实而安全（例如「这次调用只会删掉已失效的缓存项，别的什么都不做」）。找出这个事实写成一句话，把时间花在证明它上，而不是列一长串「可能」。把握度阶梯：只是说了 → 指到 `文件:行`（或依赖库源码） → 推演坏情况走不到 → 写脚本或测试调用真实代码、错了就响亮失败 → 在运行的应用里复现。尽量往下走，写明停在哪一级；证明不了写「未证明」。grep 看不到的地方要专门看：依赖库源码与锁定版本、执行时机（微任务、卸载、后台标签页）、API 返回的 JSON、数据库列、线协议、功能开关、下游三跳。
- **攻击前提**：两次修复都没过同一关，先把它们共同的前提写成一句话并验证（见 `principles.md`），再写下一个修复；不是换个写法再试。
- **两种形状**：跨函数边界的改动，先画两种不同的形状（类型、签名、模块边界），选每份状态只有一个写者、每件事只有一种做法、调用方要知道的最少的那个。
- **方向有分叉、读代码定不下来**时，先用一次性小原型（隔离 worktree、只验证分叉点、不进主分支）拿到证据再裁决。
- **重要方案**在 design 里写「借鉴与取舍」（成熟方案怎么做、采用哪部分、为什么）和「规模假设与性能预算」，写不出就不进入实现。

| 档 | 什么时候 | 做什么 |
|---|---|---|
| A 最小完整修复 | 根因单点 | 修复，同一表面由红转绿，加防复发 |
| B 局部重构 | 同一机制 ≥2 处，或修复要再加一条并行路径 | 收敛成单一写者或判据 → 迁移调用点 → 删旧路径 → 加守卫 |
| C 重设计 | 超出本轮或无法安全验证 | 带证据告诉用户，同意后先止血，另起变更 |

proposal 裁决段：根因机制（X 在 Y 条件下导致 Z，因为 W，附 `文件:行`）；关联问题或「扫描为空」；补丁气味；裁决与被否决方案。防复发优先级：架构消灭 > 类型 > 断言 > 测试 > lint（报错写明该用什么）> 文档；删旧路径后旧符号 grep 为零。
