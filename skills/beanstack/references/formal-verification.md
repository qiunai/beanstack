# 形式化验证与状态图

测试只检查有人想到要写的情况；形式化验证检查一个声明范围内的全部情况：模型里所有步骤的先后顺序、某个上界以内的所有输入。用在 bug 代价最高、测试最够不着的地方：并发与锁、重试与幂等、状态机（登录、账号切换、同步、支付流程）、协议、解析器。不替代 TDD：确定性行为仍然先写测试。

## 什么时候用

- 同一个竞态、时序或状态错乱类 bug 修过两次以上，或排查时说不清「所有可能的先后顺序」。
- 提案涉及多个参与者共享状态（多标签页、多设备、前后台、离线回放）。
- 用户要求「证明它不会出现 X」。

## 让问题选工具

- 「事件能否以坏的顺序发生」：对设计建一个小模型用模型检查器，默认 TLA+ 加 TLC。
- 「代码本身是否对每个输入都成立」（不变式、溢出、边界）：优先跑在真实代码上的工具；该语言没有这类工具时，用基于属性的生成式测试或模型对照测试驱动真实代码，不要手写一份函数的模型。
- 选开发者能装能跑的工具，交付里说为什么选它。需要装运行时（例如 TLC 要 Java）而当前机器不能装时，写「本机测不了」，交给能装的机器。

## 做一个检查

1. 从代码里挑目标：代码对用户的一个承诺，破了会伤用户、测试很少能走到。挑最重要的，不挑最好验证的。用户点名的区域或 bug 优先。
2. 一句白话写下属性和破了的危害。
3. 建模：模型里每个部分都能指到一段可打开的代码；代码里一个不可分的步骤，模型里也是一步；名字用项目里的名字。
4. 证明它会失败：在一个故意改坏的代码变体上（删掉一个检查、调换两步）跑，必须报错。从没见它失败过的检查什么也证明不了。
5. 当前代码违反属性时，把反例按代码里的步骤讲成一串，作为发现上报；不削弱属性或模型去让它通过，用户没要求时不改产品代码。
6. 写清范围：验证了什么、在什么上界和假设下、没覆盖什么。通过只覆盖模型或上界内的情况。
7. 留一个项目内的检查技能或脚本：一条命令、固定工具版本、跑得够快；记录每个检查覆盖哪些文件和函数，以及最后确认模型与代码一致的提交号。按它的步骤自己走一遍，在故意改坏的代码上确认能抓住，再撤掉改动。

## 读结果：状态图

- 用 Mermaid 画状态图给负责这块行为的人看：状态用读者看得到或关心的话命名（「已登录、本机库仍是上个账号」），箭头用用户看到的事件命名（「切换账号」「网络断开」），条件写在方括号里。不出现变量名和动作名。
- 违反规则的状态单独标出，图例写清违反哪条；给出从初始状态到它的最短路径，按步骤讲。
- 保持 20 条箭头以内：先合并表现一样的状态，再隐藏每个状态都有的重置类箭头；不要合并违反不同规则的两个状态，隐藏了哪些步骤在交付里说明。
- 模型检查器越过违规状态后还会继续，所以图上会出现 bug 之后的状态，读的时候要区分。

## 代码变了以后：同步模型

模型和代码不同步时，检查会继续通过，却证明的是已经不存在的代码，这是最危险的情况。改到被覆盖的代码、合并、重构之后：

1. 先按原样跑一次，记结果；此时的通过只说明旧描述仍成立。
2. 读从记录的同步提交到现在、所有改到被覆盖代码的提交（含改名、拆分、挪文件，和新写入同一份状态的代码）。每处判断：没影响；代码形状变了，模型要改；承诺被有意改了（要有文档、测试、提交说明作证据），属性要改；承诺可能被破坏。
3. 先按代码改模型，再重跑，不按「怎样能过」改。属性只为有意变更的承诺改，写下旧写法、新写法和证据。上界非改不可时在交付里说明。
4. 判结果：通过的要再在故意改坏的新代码上确认能抓住；失败的把反例逐步对照真实代码，有一步在代码里不可能发生就是模型错了，每步都能发生就是代码 bug，找出引入它的提交。
5. 每个检查给一个结论：一致、已更新、代码 bug、受阻（写明原因）。说清哪些失败是模型漂移、哪些是代码 bug；原来通过、更新后失败的，说明原来那次通过是在过期描述上。
6. 更新覆盖记录和同步提交；受阻的不前移同步提交。模型更新单独成一个提交，不和产品修复混在一起。
