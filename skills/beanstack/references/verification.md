# 验证与 TDD

用最便宜又能真实证明行为的方式，命令以项目验证速查表为准。本机测不出的靠上线后冒烟和回滚兜底。开发期间只跑受影响的验证，全量交 CI。

## TDD

能用确定性测试表达的行为（逻辑、协议、数据、脚本、守卫）先写验收测试，确认它因正确原因失败，单独提交，再实现到通过。重构先补锁住现有行为的测试。纯视觉走视觉验收，性能走基准。

## 证据

- 写明命令、退出码、版本、日志位置。bug 要有同一表面的「修复前失败 / 修复后通过」。结果只有通过、失败、受阻。
- 证明和用户说法同一层：「点了没反应」要在真实界面点出反应。只在替身或功能关闭环境证明过的写「未实测」。
- 新检查要指出它本可拦住的一次真实错误；已不可能再发生的错误删掉对应检查。新测试不读产品源码做字符串断言，改用行为、AST 或依赖图检查。

- 每个结论标出把握：实测（附命令或证据位置）、推断、未验证。能自己跑的检查不交给用户去跑。
- 测试覆盖不到的并发、重试、状态机问题，按 `formal-verification.md` 做形式化验证。

## 性能与数字

报告或依据一个测出来的数字（提速、回退、吞吐、延迟、评测结果）之前：

1. 跑之前写下要发布的那句话（「导出在 6 万行数据上 p50 快 30%」）和「什么结果会改变决定」；读一遍测量脚本，看它计时、计数、忽略了什么；看机器负载，忙的话交替跑两边并写明。
2. **为什么不是两倍**：说出限制它的资源或代码路径，证据来自一次不报告的剖析（CPU 剖析、每进程 CPU、I/O 等待、系统调用计数）。读代码猜出来的不算。改动没让数字变，也要靠限制因素解释。
3. **两边都调优了吗**：都按生产方式跑（生产构建、生产配置、同样的缓存冷热、同样的版本和数据）。一边用默认配置，比的就是配置而不是实现。
4. **超没超物理上限**：拿带宽、核数、被改部分原本占的时间算一算。去掉占 10% 的部分最多快约 11%；超过上限说明测到了缓存、空操作或 bug。
5. **有没有报错**：数失败和非成功响应，核对输出正确而不只是存在。拒绝往往很快，超时和重试往往很慢。
6. **能不能复现**：每边至少 5 次、交替跑（A、B、A、B），报中位数和范围；差距小于两次运行间的波动就是「没有可测差异」。
7. **重要吗**：微观结果旁边测一次用户真正等待的端到端路径，用真实数据量和并发，写出微观结果占整体的比例。
8. **工作真的发生了吗**：确认工作在计时区间里跑了（请求到了、行写了、结果被用了）。没人迭代的生成器、没人等的 promise、被优化掉的结果都会给出假数字。

结论先写：更快、更慢、没有可测差异、或无法判断。附数字和单位、次数、范围、限制因素，例如「p50 41ms→33ms，每边 7 次中位数，之后范围 32 到 35ms，瓶颈是单核 JSON 解析」。说不出限制因素、一边没调优、或第 5、8 条没查的，结论写「无法判断」并说明缺口。PR 正文只放一个主要数字，过程放证据文件。

## 持续优化一个指标

把一个能测的数反复推到目标（识别准确率、首屏时间、包体、耗时）时用；一次性修复按 bug 或性能流程走。

1. 先选能复现用户抱怨的真实场景和数据规模，写测量脚本；用一易一难两组负载证明它测得出差别，然后冻结，之后不改。
2. 开一份不进仓库的决策日志，每次尝试一行：假设、改动、改前、改后、差值、测试结果、保留或回退。每次动手前先读一遍。
3. 每个假设点名具体机制（「把 X 挪出启动路径，因为它挡住首屏」），不写「试试加缓存」。
4. 一次只改一处、测一次：超过运行间波动且回归测试仍绿才保留，否则整个回退；保留的单独提交。不叠加没测过的改动，不凭读代码宣布变好。
5. 连续几次没进展时换一类做法、组合差一点成功的尝试、重读源码，再判断是否到顶。正确和简单优先于数字。

找性能修法按从便宜到贵的顺序试，前一种够了就停：不做（结果没人用就删掉）→ 不重复做 → 少做 → 晚点做 → 趁用户不注意时做 → 并发做 → 做得更便宜。

## 运行时取证

卡死、内存泄漏、界面抖动、CPU 飙高这类问题，先抓真实信号再推理，不从源码猜。

- 在出问题的表面上抓 CPU 剖析、堆快照、性能录制或日志。已经有录制就读它，不重跑。
- 大文件交给子代理解析，必要时导进 sqlite 按样本、帧、节点查询；协调器只收结论。
- 收窄到：占时最多的调用路径；泄漏对象到 GC 根的引用链；没有输入却还在跑的循环。
- 先证实机制再相信：在运行中的进程里加探针或临时改代码验证。有前后两份录制就对比；没有就写「录制支持的最强假设」，不写成已确认的原因。
- 落到源码的文件、符号和行。交付是带出处的诊断，用户没要求就不修，修复转 bug 或性能流程。

## 同类排查清单

修一个问题前、冻结前对照查一遍：

| 查什么 | 坏法 |
|---|---|
| 计时断言 | 一两秒的绝对门槛在高负载下误红；改成上限设长、门槛取其几分之一，反例数调用次数 |
| 外部调用总时间 | 各有超时但没有总预算 |
| CI 与本机差异 | 依赖全局 git 身份、CI 专有环境变量、进程名（Linux 上 Node ≥24 是 `MainThread`）、时区、大小写 |
| 构建脚本写回源文件 | 本地一跑工作区就脏 |
| 增量选择盲区 | 读源码文本的契约测试、登记清单类守卫选不到，点名跑 |
| 包体预算 | 改前端运行时代码后就跑；超了先拆包，抬预算要用户同意 |
| 新测试没登记、写了本机绝对路径 | 同时登记，用临时目录 |

思路来源：持续优化、性能修法顺序、运行时取证改写自 pstack 的 hillclimb、perf-issue、runtime-forensics、trace-forensics（cursor/plugins，MIT）。
