# 开工对齐

非简单任务的第一条回复。目的：用户只描述想要的效果，协调器先把它翻译成专业人士会怎么定义、怎么做、怎么验，再开工。一句话改动跳过。

## 三步，写成一条回复

1. **复述**：一两句说出你理解的目标、要解决的问题和最小改动。从用户原话、附图和相关文件出发，不从摘要出发。
2. **行话**（用户在描述画面或感觉、没用到这个领域的术语时做；用户已经用准了就跳过）：
   - 描述可能指两三种不同问题时，先列出来，每种给命名它的术语和区分它的信号，再说你按哪种理解、为什么。
   - 给 3 到 8 个术语（大任务可到 12 个），按「对做出来的东西影响多大」排序。每个写：英文原名和通行中文名都给（如 slide-in 滑入、overshoot 回弹缓动；没有通行中文名的给直译并注明），一句白话意思、对应用户原话的哪部分、一个真实用到它的项目或文档链接、有了它能向代理或检索要什么。
   - 需要时借一两个邻近领域的说法，说清哪里能借、哪里不成立。
   - 点出用户没提但应该关心的点（无障碍、性能、离线、边界状态、回退）。
   - 用新词把需求重写一遍。
3. **改深**（不是改大）：
   - 这个领域的顶尖做法会比用户要求的多做什么。
   - 应该从什么最原始的材料起步（真实数据、原始日志、规范原文、上游源码），而不是二手总结。
   - 用哪些成熟方法和工具。
   - 除了协调器和用户自己，什么能证明结果对（规范、基准、真实用户路径、对照实现、外部检查器）。这一条写进验收判据。

## 规则

- 链接要打开确认它确实这样用这个术语，确认不了就删掉。术语和现成方案的检索可以和代码侦察并行派给检索通道，结论核实后才写进来。
- 改深只加深度，不加范围；新加的范围算建议，交用户决定。
- 能用实验定的分叉（哪种实现、时序、参数）不问用户，按 `architecture.md` 用一次性小原型定，再推荐；产品和偏好类的取舍留给用户。
- 对齐后直接开工，不等确认。只在项目停止条件处停下问；描述对应多个问题、选错要返工的，算产品取舍没有定论。要问就一次问完，每题给推荐答案。
- 对齐的结论（术语、改写后的需求、外部检验点）写进需求核对表或提案，后续子代理任务书沿用这些术语。

## 例子

用户说「卡片从左往右弹跳入场」。行话：入场动画（entrance animation）、从左滑入（slide-in from left）、回弹缓动（overshoot / back easing）或弹簧动画（spring，刚度 stiffness、阻尼 damping）、错峰入场（stagger）、减少动态效果偏好（prefers-reduced-motion）。改深：动效规范会规定时长区间和只动 transform / opacity；外部检验点是逐帧录屏看有没有掉帧、开启减少动态效果时是否退化成淡入。

思路来源：pstack 的 in-your-own-words、reframe、sharpen（cursor/plugins，MIT），按本工作流改写。
